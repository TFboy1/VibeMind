以下是明确支持边界，继续保留，不以增加框架掩盖：

- A05/A06/A07、H01/H02/H03/H04：只支持同一学习者、同一系统、本机可靠磁盘。UNC 写入拒绝；不能检测所有网络挂载/映射盘。未建设远程 HTTP、鉴权/多租户、跨设备离线合库或实时同步活库。
- C04/C05/C07、E05/E06：工具拒绝版本覆盖，但不做自动语义合并、概念合并或锁住完整教学会话；两个独立会话仍可能同时解释。真实事实/授权由当前会话核实。
- B05/B07/B08、A08/A09/G08：升级需完整 Skill/CLI/MCP、依赖与进程重启；新宿主首次核对连接。安装/读取不启用伴学，不接管未安装宿主的配置，也不保证模型自动执行 Skill。
- D07/D09：独立复制/worktree 保持独立项目语义，没有逻辑项目与多个 checkout 的共享关系。
- E01/E03/G04：summary 不清洗摘要内所有秘密；策略不是用户 ACL。未加密，不保证物理安全擦除或删除外部备份/聊天，Windows POSIX mode 不等于 ACL。
- F04/F07/F10、G03：没有自动改 Git 忽略规则、自动清理历史或在线覆盖式恢复。保留 hot journal，离线恢复必须停写并核验；需显式轮换 ID，普通文件替换无法自动识别恢复。
- 路径大小写、断电、杀毒占用、磁盘满等不宣称跨平台实机全覆盖；现有回归验证关键事务/身份断点、备份发布故障和平台门槛。

## 历史：初始化和后来安装宿主

现在有文字要求，但初始化没有强制验证共享存储的一致性。

- SKILL.md 第 23 行要求不同宿主的 VIBEMIND_HOME 必须一致；README.md 第 91 行也说明同机共享目录。
- storageLocation() 默认选择 os.homedir()/.vibemind，优先接受 VIBEMIND_HOME；没有按 Codex、Claude Code、WorkBuddy 分库。
- initialize() 返回 memoryHome/databaseFile，却没有保存数据库的唯一身份或校验当前项目以前连接的数据库。APPLICATION_ID 是格式标记，不是每个数据库各自唯一的 ID。
- project.json 目前只保存 schemaVersion 和 projectId，不能识别“这个 ID 属于另一个记忆库”。
- 初始化不登记已安装宿主，也不会给后来安装的宿主自动配置路径。无需预先安装全部宿主，只需每个新宿主首次使用时连接同一记忆库并检查兼容性。

先在 Codex 初始化、后来安装 Claude Code：只要新宿主运行在同一实际用户环境，选择同一个记忆目录、同一项目身份和兼容版本，就可以读到原来的学习记录，重复 init 无变化。这一点已用不同安装目录的 CLI 验证。

真正危险的是新宿主用了另一个 VIBEMIND_HOME、另一个系统用户目录或旧版本 CLI。当前 init 在“project.json 已有 ID、所选数据库没有该 ID”时仍可新建空项目行，造成两份数据库同时持有同一个项目 ID。原数据库没有被删除，但用户会看到一份空的学习历史，并可能继续向两个库分别写入。

## 原始 72 项边界与解决办法

“已处理”表示代码有相应保护，不能推导为已覆盖所有操作系统故障或实际宿主行为。
“缺口，已复现”表示额外隔离脚本验证了当前不理想的结果。
“部分处理”表示数据库保护存在，但 Agent 流程、诊断、内容合并或恢复仍有不足。
“使用边界”表示应明确产品语义或部署前提，不一定需要新增功能。
P1 优先处理错误分库、过期指令覆盖、旧写入器绕过和初始化恢复；P2 改善可观测性、使用流程和内容质量；未来项仅在支持远程、多设备或多用户时实施。

| H01 | NAS/SMB/同步盘实时共享一个 SQLite 文件 | 未作为安全部署方式实现；网络锁语义或多份文件同步无法依赖当前本地事务保证 | 使用本地可靠磁盘；跨设备经服务操作服务端本地数据库，不同步活库文件；单服务仍可用 SQLite |
| H02 | 给当前 stdio 服务简单加 HTTP 就作为远程服务 | 未实现：locate/目录校验假定项目在服务所在机器，backup 允许调用者选择本地绝对输出路径 | 远程接入先定义逻辑项目 ID、客户端来源声明和身份绑定；限制备份导出目录；HTTPS/鉴权/用户隔离；不能原样开放本地文件接口 |
| H03 | 多台设备离线各自学习，后来合并或迁移两个已有库 | 未实现合并协议；覆盖 memory.sqlite 会丢另一份增量，别名/偏好/撤销可能矛盾 | 需要时做结构化导出/导入：稳定事件 ID、墓碑和冲突报告；证据可追加，档案/地图冲突显式整合；暂不承诺自动离线同步 |
| H04 | 多个人共用同一系统账号/数据库，或远程部署多个用户 | 使用边界：目前是一位学习者的用户级记忆，没有多租户身份与权限 | 本机不同学习者分库；远程按真实登录身份隔离，服务端强制 owner 和访问范围；历史授权文字不能作为远程工具权限 |

SQLite 官方提醒网络文件系统锁与同步行为不可靠，可能破坏数据库一致性。服务与 SQLite 文件放在同一机器，通过 API 访问可以避免直接共享远程数据库文件。[SQLite 网络使用说明](https://www.sqlite.org/useovernet.html)

## 推荐初始化流程

无需要求用户先安装所有宿主，也无需轮流询问是否安装 Claude Code、Codex、WorkBuddy。

1. 新宿主首次使用先只读解析用户配置、VIBEMIND_HOME 和实际存储位置，返回 storeId、API/软件/schema 版本、执行环境及项目定位。
2. 项目身份与当前记忆库匹配：读 context，继承暂停状态、学习范围和全部未完成决定，接续即可。
3. 尚无项目身份且用户明确启用：在已选定的共享存储中初始化，返回可核对的路径、库 ID 与项目 ID。
4. 已有项目身份而当前库没有记录或库 ID 不匹配：报告连接/记录缺失，阻止自动空建；明确连接原库、恢复备份或建立独立项目的意图。
5. 存在旧 state.json：在可恢复的初始化流程中校验、导入并保留原字节；旧项目地图和自由文本保持历史，不自动当最新架构或已掌握证据。
6. 后来安装的新宿主执行同一流程，使用既有用户配置；正常接续不需要再次创建学习档案。

首次启用时应清楚展示“这个项目连接哪个用户记忆库”和“跨项目可共享哪些内容”；不要求用户理解每个平台的安装目录。
如果用户明确用 VIBEMIND_HOME 建立隔离库，应尊重该选择，并明确连接已有项目身份的行为，不能静默整合多个库。

## 当时推荐的实施顺序

第一批解决 P1：

1. 加强 status 原因区分与共享库识别，阻止 A02/D05 的静默空建。仅添加路径提示不够。
2. 设定兼容写入器门槛。由于旧 0.2.0 会检查 user_version，升级数据库格式版本比仅新增“建议升级”的元数据更能阻止旧程序继续按旧规则写入。迁移保留备份并覆盖旧客户端拒写用例。
3. pause/resume 加状态版本，提供稳定 operationId/提交回执以处理不确定重试；过期用户指令不能被自动重放。
4. 初始化增加明确的中断恢复步骤，覆盖文件身份与数据库事务间的断点；不是把写入顺序调换就能覆盖所有崩溃。
5. 完善冲突信息和按 ID 读完整记录的入口，让 Agent 能正确整合同一卡片与替换字段。

第二批处理共享范围/来源、健康项目列表容错、分页、运行时诊断、输入提前限额和备份完成标记。
多设备远程服务、离线合并、多用户只在这些能力成为明确目标时建设；同机多个宿主共享无需增加 Web 前端、队列、Redis 或通用同步框架。

## 当时提出的验收条件

下列是建议实现时需要通过的条件，目前不能宣称已经满足。

| 验收项 | 应看到的结果 |
| --- | --- |
| 不同安装目录、同一共享库 | 项目/库 ID、revision、卡片、暂停状态一致；重复 init 无变化 |
| 已有项目身份、切到错误/空库 | 明确库不匹配或记录缺失，拒绝空建；原库与身份不被改写 |
| 0.2.0 访问新兼容门槛后的数据库 | 写入拒绝并保留文件，新版仍能读；旧来源规则无法绕过 |
| 同项目多个进程并发记录 | 冲突可识别，整合后双方内容保留；只改 revision 的旧内容不能作为合并方案 |
| 不同项目并发通用档案写入 | userRevision 保证冲突，来源保留；其他活跃来源正常工作 |
| 提交成功但丢响应、同 operationId 重试 | 只产生一次实际更新，返回原提交回执；不同 payload 重用 ID 明确拒绝 |
| 新暂停之后提交旧 resume | 版本冲突，保持暂停；重复已完成请求不翻转当前状态 |
| 初始化各个断点失败/进程终止 | 状态可诊断和恢复，没有无法辨认的孤立身份；既有记录不被覆盖 |
| 单个项目状态坏了 | 健康项目仍可发现，坏项目保留并返回独立错误 |
| 私有项目参与全局概念查询 | 不返回不允许共享的项目正文，已允许的通用学习范围仍能查询 |
| 历史数量超过 100、读取中持续新增 | 可稳定分页、核对准确范围，没有因为截断而误判全部讲过 |
| 超大输入进入 CLI/MCP | 在产生不可接受内存分配之前拒绝；没有部分提交 |
| 备份中途被杀、恢复时存在旧会话 | 半成品不冒充有效备份；恢复后拒绝旧库代际的写入 |
| 实际三个宿主接入 | 能发现工具、识别业务错误、核对同一库、处理冲突、重启保留记录；模型遵守解释/记录规则需另做真实会话验收 |
